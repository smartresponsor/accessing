# Market Analysis — Accessing

Периодический маркетинговый/продуктовый анализ приложения **Accessing** в контексте портфеля из 46 самостоятельных bounded-context приложений (`D:\PhpstormProjects\www`). Разделы добавляются сверху, от новых к старым, каждый раз при очередном проходе ротации маркетингового анализа. Этот файл дублирует `MARKET_ANALYSIS.md` из корня репозитория и предназначен для публикации через GitHub Pages, если репозиторий будет так настроен.

## Анализ рынка — 2026-07-10

### Граница ответственности

**Что делает приложение.** Accessing (`accessing/access`) — Symfony-компонент, владеющий полным жизненным циклом доступа пользователя: регистрация и активация аккаунта, аутентификация, второй фактор (TOTP и Passkeys/WebAuthn), верификация email/телефона, восстановление доступа (сброс пароля, коды восстановления), троттлинг попыток входа и учёт событий безопасности. Это переиспользуемый "кирпич" экосистемы, а не отдельный продукт для конечного покупателя.

Границы зафиксированы в собственном `BOUNDING_MANIFEST.md` приложения:

- **Входит в зону ответственности:** регистрация/активация доступа; владение и обслуживание учётных данных; верификация email и телефона; включение и прохождение второго фактора; сброс пароля и коды восстановления; попытки входа, кулдауны, блокировки/разблокировки; сессии доступа и учёт событий безопасности; UI/CLI/фикстуры/тесты/отчёты, необходимые для этих потоков.
- **НЕ входит в зону ответственности:** обобщённое управление профилем пользователя; администрирование организаций/тенантов; полноценный движок политик авторизации (это домен Rolling); платёжные идентификаторы и платёжные инструменты (Billing/Paying); архив юридических согласий; глубокий KYC/AML; функции центра уведомлений (это домен Messaging).

Технически это Symfony security-бандл (`scheb/2fa-bundle`, `symfony/security-bundle`, `symfony/rate-limiter`, `symfonycasts/reset-password-bundle`, `symfonycasts/verify-email-bundle`), встраиваемый в приложение-хост (`App`, `smartresponsing/app`), с прямыми путевыми зависимостями на `Objecting`, `Configuring`, `Interfacing`.

### Карта соседей по www

Просмотрены `composer.json` (name/description) и верхнеуровневая структура `src/` всех остальных 45 приложений из фиксированной ротации.

**Семантически ближайшие соседи:**
- **Rolling** (`rolling/role`) — роли и авторизация (`Policy`, `Security`, `Voter`-подобные концепции). Чистое разделение: Accessing = *аутентификация* ("кто ты"), Rolling = *авторизация* ("что тебе можно"). У Accessing в `src/` нет папки `Voter`/`Policy` — подтверждает, что разделение соблюдается на практике.
- **Vaulting** (`smartresponsor/vaulting`) — управление инфраструктурными секретами (AWS Secrets Manager/Vault). У Vaulting есть отдельный документ `docs/identity-access-boundary.md`, явно разграничивающий "identity" в его смысле (identity разработчика/CI/workload через AWS IAM/OIDC для получения временного доступа к секретам) от identity конечного пользователя приложения. Прямая цитата из документа: *"Do not allow ordinary application user OAuth tokens to read infrastructure secrets."* Пересечения по коду нет, но терминологическое сходство ("identity", "access") может путать при поиске — стоит явно ссылаться на этот документ в документации Accessing.
- **Messaging** (`messaging/message`) — имеет собственный `src/Authenticator/Message/MessageOidcAuthenticator.php`. Это стандартный Symfony-файрвол для защиты собственных API-роутов Messaging через OIDC, а не дублирование пользовательской аутентификации Accessing. Реального пересечения кода нет, но это сигнал: если Accessing когда-либо добавит OIDC/SSO для конечных пользователей, стоит заранее согласовать общий подход к OIDC-интеграции с Messaging, чтобы не плодить две независимые реализации OIDC-клиента в портфеле.
- **Administering** (`administering/administration`) — обобщённый инструментарий governance (`Auditor`, `Guard`, `Recorder`, `Voter`, `Scanner`). У Accessing есть собственный `src/Recorder/SecurityEvent` и `src/Service/SecurityEvent`. Это потенциальная точка дублирования: неясно, должен ли аудит событий безопасности Accessing утекать в общий Recorder/Auditor Administering, или Accessing намеренно ведёт независимый узкоспециализированный журнал. Конкретные файлы для сверки: `Accessing/src/Recorder/SecurityEvent/*`, `Accessing/src/Service/SecurityEvent/*` vs `Administering/src/Recorder/*`, `Administering/src/Auditor/*`.
- **Gating** (`gating/gate`) — несмотря на похожее по звучанию название, это инструмент governance для экосистемы репозиториев/CI (`Console`, `Inventory`, `Policy`, `Rule`, `Target`), а не gate доступа пользователей. Пересечения нет.

**Пустые/подозрительные точки, проверенные точечно:**
- `Accessing/src/Catalog` — папка существует, но пуста (0 файлов). Похоже на неиспользуемый артефакт, а не на пересечение с доменом `Cataloging`. Стоит либо удалить папку, либо заполнить осмысленным содержимым (например, каталог доступных ролей/уровней доступа), чтобы не вводить в заблуждение.

**"Ничейные" зоны (логически нужны, но не покрыты явно):**
1. **Social login / внешний IdP для конечных пользователей** (Google/GitHub/Apple OAuth, SSO для B2B-клиентов). В зависимостях Accessing нет `HWIOAuthBundle` или аналога, ни у одного из 46 приложений явно не просматривается ответственность за пользовательский social login/SSO-федерацию (Vaulting и Messaging решают смежные, но не эту задачу — см. выше). Это одновременно и разрыв с рынком (см. раздел Gaps ниже), и белое пятно портфеля.
2. **Юридический архив согласий (GDPR/consent)** — явно исключён из зоны Accessing собственным манифестом. В корне `www` есть папка `Complying`, но она **не входит** в фиксированный список 46 приложений ротации — то есть в рамках текущего портфеля из 46 эта ответственность формально ничья.
3. **Централизованный аудит событий безопасности** — см. пункт про Administering выше: неочевидно, кто источник истины.

### Ландшафт рынка и лидеры (2026)

Зона ответственности Accessing соответствует рыночной категории **CIAM (Customer Identity and Access Management)**. Актуальные (2026) лидеры и альтернативы в этой категории:

- **Auth0** (Okta) — самый узнаваемый CIAM-бренд, движок Actions для кастомизации; в 2026 расширил бесплатный B2B-тариф (25 000 MAU, self-service SSO/SCIM включены).
- **Okta / Okta Customer Identity Cloud** — после поглощения Auth0 усилил позиции в CIAM, ориентирован на предприятия с высокими требованиями к governance.
- **Keycloak** (Red Hat, open source) — self-hosted, Apache 2.0, без лицензионных платежей за пользователя; SSO, identity federation (LDAP/AD), SCIM, fine-grained authorization "из коробки" на всех тарифах (в отличие от Auth0, где SAML/SCIM — платные enterprise-функции).
- **AWS Cognito** — управляемая аутентификация, глубокая интеграция с экосистемой AWS.
- **FusionAuth** — self-hosted как основная модель развёртывания, полный набор CIAM-возможностей, ориентация на организации, которым нужен полный контроль над инфраструктурой аутентификации.
- **WorkOS (AuthKit)** — в 2026 расширился до полноценной платформы user management, бесплатно до 1 млн MAU, включая social login, MFA, RBAC и passkeys; исторически силён в enterprise-онбординге (prebuilt SSO/SCIM).

### Gaps и возможности

**(a) Что лидеры делают, а Accessing — нет, в рамках его собственной зоны:**
1. Passkeys/WebAuthn backend и ceremonies уже реализованы; остаются release acceptance, host-installation proof, browser/Twig UX, migration verification и interoperability coverage.
2. Push-уведомление как метод второго фактора (мобильный authenticator-push) — отсутствует.
3. Social login для конечных пользователей (Google/GitHub/Apple OAuth) — в зависимостях `composer.json` нет OAuth-клиентского бандла.
4. Adaptive/risk-based authentication — оценка устройства, гео-аномалий ("impossible travel") — есть только базовый rate-limiter, нет поведенческого анализа.
5. Проверка на "утёкшие" пароли (интеграция вида HaveIBeenPwned) при регистрации/смене пароля — не просматривается в зависимостях/сервисах.

**(b) Где у Accessing может быть преимущество:**
1. **Self-hosted, без per-MAU биллинга** — у Auth0/Cognito/WorkOS стоимость резко растёт с ростом MAU (по данным рыночного обзора — на 500 000 MAU счета Auth0 могут достигать пятизначных сумм в месяц); Accessing как встраиваемый Symfony-бандл этой стоимости не несёт.
2. **Архитектурная целостность экосистемы** — Accessing уже физически завязан на общий контрактный слой портфеля (`Objecting`, `Configuring`, `Interfacing`) и рядом с `Rolling` для авторизации; интеграция с внешним SaaS IdP потребовала бы отдельного сетевого хопа и синхронизации состояния для каждого из 46 приложений, тогда как здесь это единая кодовая договорённость.
3. **Точная доменная терминология без обёрточных абстракций** — собственный `BOUNDING_MANIFEST.md` запрещает generic-обёртки вроде `AccessUser*`/`UserSession`, что даёт более чистую модель, чем универсальный SaaS IdP, который навязывает свою обобщённую модель пользователя/сессии.

### Итог — топ-5 рекомендаций

1. Довести существующую реализацию Passkeys/WebAuthn до release acceptance: подтвердить host-generated migrations, end-to-end API/Twig/browser flows, RP/origin/proxy configuration, fallback UX и interoperability; `web-auth/webauthn-lib` уже является production dependency.
2. Рассмотреть добавление social login (минимум Google) через стандартный OAuth-клиентский бандл — сейчас это явный пробел против всех пяти рассмотренных лидеров.
3. Согласовать с командой Administering, должен ли `Recorder/SecurityEvent` Accessing быть источником данных для общего аудита экосистемы, или это намеренно независимый журнал — сейчас это неопределённость на границе, а не подтверждённое архитектурное решение.
4. Удалить или наполнить осмысленным содержимым пустую папку `src/Catalog` — в текущем виде это шум на границе ответственности.
5. Точечно оценить лёгкую проверку "утёкших" паролей (например, k-anonymity API по образцу HaveIBeenPwned) при регистрации и смене пароля — сравнительно дешёвая функция с ощутимым улучшением security posture, которая пока отсутствует.
